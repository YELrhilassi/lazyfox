## 2a. `;o` + a bare word was the way in — DONE

The user supplied the reproduction: `;o`, then one ordinary word like
"doodle" — no dot, no scheme. `;o`'s Enter path ran every value through
`core.normalizeUrl`, which unconditionally prepends `https://`. So "doodle"
became `https://doodle`, failed DNS, and dropped them on a Firefox error page
— where no content script runs, so neither the leader nor the which-key overlay
can be reached, and the URL bar that would rescue them is hidden by Lazyfox's
own chrome CSS. That is how a single typed word reached a dead end, and it is
also why relaunching reproduced it: session restore reopened the error tab.

`;o` now asks `core.isLikelyUrl` first — the same predicate the command-center
input has always used (scheme, domain dot, or localhost means URL; anything
else means search). A bare word searches. Only something that looks like a host
is navigated to.

The core already had `IsLikelyUrl` in `core/url.go`; `;o` simply never
consulted it while the command center did. This is the whole fix.

Note: no e2e test was kept for this. An attempt asserted on the opened tab, but
a real search opens an external tab the harness cannot settle deterministically,
and it destabilised the two tests after it (tab indexes shift). The behaviour is
now identical to the command-center path, which is covered; the error pages that
the user could otherwise still reach are covered by 2b's endpoint tests.

## 1. `;G` / `;L` did nothing — DONE

`;G` and `;L` were registered as two-key *sequences* (`;G` then `k`) on the
reasoning that this let the shifted keys "never shadow" a plain binding. Shift
already makes `G` a different key from `g`, so the extra key bought nothing and
cost the feature: `;G` armed a one-shot capture, showed nothing, and on timeout
fell through to a plain `G` action that **does not exist**. The which-key table
advertised `;G` the whole time.

Both are now plain bindings (`src/chrome/main.ts`,
`src/extension/content/main.ts`). Verified in the e2e suite: `;G opens the
navigation-stack popup`, `;L opens the navigation-stack popup too`, and the
pre-existing `;g back and ;l forward` confirms the lowercase pair is intact.

## 2. Dead keyboard on loading / error pages — PARTIAL, and the diagnosis is uncertain

### What changed

`chromeOwnsKeys` (`src/chrome/keystate.ts`) used to hand every `http(s)` URL to
the content script on the strength of the URL alone. It now hands over only when
the content script is actually **present** — it sets `data-lf-content` at
`document_start`. An unreadable document counts as absent, which is the case
that matters.

Rationale: between a navigation starting and its response arriving,
`currentURI` is already the target URL while no content script exists, so the
chrome helper deferred and nothing answered. That window also covers DNS
failures before Firefox swaps in `about:neterror`, and session restore reopens
the same tab — which is why relaunching reproduced the stuck state.

Seven unit checks pin the rule (`scripts/test-chrome-keys.ts`, 15 → 25).

### What we could NOT establish

**The e2e tests for this do not reproduce the bug.** `scripts/e2e/suites/content/stuck.ts`
covers a never-answering endpoint, a stalled body, HTTP 401/403/404/500/502/503/504,
`about:config` and `view-source:` — 13 tests, all passing. But they also pass
with the ownership fix reverted. So they are **coverage, not proof**: they show
the keyboard works on those pages today; they do not show the fix is what makes
it work.

Two things this rules out, worth recording so nobody re-derives them:

- Navigating an *existing* page to a hanging URL cannot reproduce it. During a
  navigation the previous document and its content script stay alive until the
  new response commits, so the keyboard keeps working. The test has to start
  from a fresh tab that has never carried a content script.
- A chrome-owned popup is **not** observable from the tab. It mounts in the
  chrome document, so `hasHost(tab, "lazyfox-popup")` returns false even when
  the popup is open. The tests assert `chromeState().leaderActive` instead,
  which is read from the chrome document and therefore can only be true if the
  chrome window consumed the key.

### Why it still may be right

There is a second mechanism that already covers content-script-less pages: the
window actor (`actor-child.ts` / `actor-parent.ts`), which forwards keys to the
chrome helper and is exempt from the deferral in `chromeKeyDown`. That is very
likely what actually serves the stuck pages today — and the most probable
explanation for the original report is that the actor is unavailable in some
states we have not reproduced (a content process that never starts, a
`currentWindowGlobal` that does not exist yet, a crashed process).

**Next step, before touching this again:** get the user's actual reproduction.
Which site hangs, whether the address bar still responds, whether the process
list shows a content process for the tab, and whether it recovers after
`about:config` in the same tab. That distinguishes "actor missing" from
"ownership wrong", and the two have completely different fixes.

## 3. Multi-key layout — NOT STARTED

The design the user asked for:

- `;` + first key = **category**, `;` + first key + second key = **action**.
- `;1` … `;9` stay exactly as they are. Where a tab index has sub-entries
  (`;1a`, `;1b`), pressing `;1` shows a small modal of the letters. **If a tab
  index has no sub-entries, no modal appears** — it just navigates. That
  "quiet by default" rule is the core of the ergonomics ask.
- No search input on that modal: quick keys only.
- Sequences must show in the status bar as leader → first key → next key.
- Do not over-nest: frequently used actions stay single-key.

Open questions that need an answer before code:

- Which existing single-key bindings move under a category, and which stay
  bare? The trade-off is real either way and it is expensive to unpick once
  users have learned a keymap.
- Category keys must not collide with the existing single-key bindings, and
  must work in both the chrome helper and the content script.

## 4. Split-restore e2e failure — NOT STARTED

` sessions: split layout is saved and restored with the session` fails when the
sessions group runs back-to-back and passes when run alone. When it fails, the
browser then loses its browsing contexts and roughly twenty further tests report
`no such frame`. Pre-existing — it reproduced before any of this session's
changes, and the version bump is not implicated (there is no version-gated logic
in the product).

The test does two `sessionRestore` calls in quick succession, so overlapping
restores are the prime suspect, but that has not been confirmed.
